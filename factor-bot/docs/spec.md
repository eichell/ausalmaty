# ТЗ: бэктест композитной стратегии Momentum + Value на акциях США

Документ предназначен для передачи Claude Code как отправная точка проекта.

> **Статус проекта.** Это исследовательский бэктест, а не торговая система. Модуль исполнения ордеров в
> объём работ не входит и не должен создаваться до прохождения всех проверок из раздела 9.
>
> Ничто в этом документе не является инвестиционной рекомендацией. Описанная стратегия может годами
> проигрывать рынку и терять деньги.

---

## 1. Цель

Построить воспроизводимый бэктест кросс-секционной стратегии на акциях США, объединяющей два фактора:

- **Momentum** — среднесрочная относительная сила.
- **Value** — композит доходностных мультипликаторов.

Плюс защитный режимный фильтр по широкому рынку.

Главный критерий успеха проекта — **не доходность, а достоверность**. Бэктест, который показывает 30% годовых
из-за look-ahead bias, хуже бесполезного: он приводит к реальным потерям. Все архитектурные решения ниже
подчинены защите от самообмана.

## 2. Что в объём работ не входит

- Подключение к брокеру, отправка ордеров, работа с реальными деньгами.
- Внутридневные данные и логика.
- Машинное обучение, подбор признаков, нейросети.
- Оптимизация параметров градиентным спуском или перебором по всей истории (см. раздел 9).

## 3. Стек

- Python 3.11+
- `pandas`, `numpy`, `scipy` — расчёты
- `duckdb` или Parquet-файлы — хранение
- `requests` + `ratelimit` — загрузка
- `pytest` — тесты
- `matplotlib` — графики
- Управление зависимостями: `uv` или `poetry`, зафиксированный lock-файл

Собственный векторизованный бэктестер на pandas. Готовые фреймворки (backtrader, vectorbt) для месячной
кросс-секционной ребалансировки избыточны и скрывают детали, которые здесь критичны.

## 4. Данные

Источники зафиксированы: **Sharadar** (исторические данные для исследования) + **Alpaca** (исполнение).
Разделение намеренное — бэктест и торговля не должны зависеть от одного поставщика.

### 4.1 Требования, не подлежащие обсуждению

| Требование | Почему | Чем закрывается |
|---|---|---|
| Данные point-in-time | Фундаментал виден боту только после фактической даты публикации | SF1, измерения AR* + поле `datekey` |
| Делистингованные бумаги | Без них survivorship bias завышает результат value-стратегий | SEP + TICKERS (`isdelisted`) |
| Корректные delisting returns | Банкротство должно давать −100%, а не исчезновение из выборки | ACTIONS + последняя цена из SEP |
| Цены с поправкой на сплиты и дивиденды | Иначе momentum примет сплит 2:1 за обвал | SEP, поле `closeadj` |
| Отраслевая классификация | Нормализация внутри сектора, исключение финансов | TICKERS (`sector`, `siccode`) |

### 4.2 Sharadar — таблицы

Доступ через Nasdaq Data Link. Базовый эндпоинт:

```
https://data.nasdaq.com/api/v3/datatables/SHARADAR/{TABLE}.json?apikey={KEY}
```

Используемые таблицы:

| Таблица | Содержание | Роль в проекте |
|---|---|---|
| `SF1` | Фундаментал, ~100+ показателей, история с 1998 | Value-факторы |
| `SEP` | Дневные цены EOD, история с 1998, включая делистинги | Momentum, оборот, market cap |
| `TICKERS` | Справочник: сектор, индустрия, биржа, `isdelisted`, `permaticker` | Вселенная, нормализация |
| `ACTIONS` | Сплиты, дивиденды, делистинги, смены тикеров | Корректность истории |
| `DAILY` | Дневные метрики (marketcap, ev, pe, pb, ps) | **Только для сверки, не для сигналов** — см. 4.4 |

**Режим загрузки: bulk, не поштучно.** Параметр `qopts.export=true` отдаёт таблицу целиком архивом.
Тянуть SF1 по одному тикеру в цикле — это десятки тысяч запросов и часы ожидания. Загружаем полные
таблицы раз в сутки, кладём в локальный DuckDB, дальше работаем офлайн.

### 4.3 Измерения SF1 — критический выбор

SF1 отдаёт одни и те же показатели в шести вариантах: `ARQ`, `ARY`, `ART` (as-reported) и
`MRQ`, `MRY`, `MRT` (most-recent-reported, то есть с учётом последующих пересмотров отчётности).

**Использовать только AR*. Использование MR* в бэктесте — прямой look-ahead bias**, потому что
пересмотренные цифры не были известны рынку в момент публикации оригинального отчёта.

Конкретно:

- Потоковые величины (revenue, net income, operating cash flow, capex) → **`ART`** (trailing twelve months).
- Балансовые величины (equity, total debt, cash, assets, shares) → **`ARQ`** (последний квартал).

Поле `datekey` — дата, когда цифра стала доступна. Это и есть `available_from` из схемы ниже.
Поле `lastupdated` в фильтрации **не участвует**: оно относится к моменту правки записи у поставщика,
а не к моменту публичного раскрытия.

### 4.4 Отдельное предупреждение про таблицу DAILY

DAILY содержит готовые `pe`, `pb`, `ps`, `marketcap`. Соблазн взять их напрямую велик, но:

- Неочевидно, на каком измерении они построены, а значит неочевидна их PIT-чистота.
- Их определения могут не совпадать с вашими (какая прибыль, какой капитал, разводнённые ли акции).

**Все мультипликаторы считаем сами** из `SEP.closeadj` и полей SF1 с AR-измерениями. DAILY подключаем
только как контрольный источник: если наш `pb` систематически расходится с их — искать ошибку у себя.

### 4.5 Ключ идентификации

Тикеры переиспользуются: одна компания может сменить символ, а освободившийся символ достаётся другой.
Соединение по `ticker` порождает тихие ошибки в длинной истории.

**Все внутренние соединения — по `permaticker`** (постоянный идентификатор Sharadar). Поле `ticker`
хранится только для отображения и для стыковки с Alpaca на этапе исполнения.

### 4.6 Роль Alpaca

Alpaca в исследовательской части **не участвует**. Причина: глубина истории с 2016 года несовместима
с протоколом раздела 9.

Задачи Alpaca:

1. **Проверка торгуемости.** Перед формированием заявок сверять список с эндпоинтом `/v2/assets`:
   поля `tradable`, `status`, `fractionable`. Часть бумаг из вселенной Sharadar на Alpaca недоступна
   (OTC, отдельные классы акций) — их надо отсеивать и логировать.
2. **Отправка ордеров** (вне объёма текущего этапа).
3. **Сверка цен.** Периодически сравнивать `SEP.closeadj` с барами Alpaca на пересекающемся отрезке
   (2016+). Расхождение больше 0.5% на ликвидных бумагах — сигнал об ошибке в обработке корпоративных
   действий с чьей-то стороны.

Маппинг `permaticker` → символ Alpaca хранить в отдельной таблице с датой последней сверки.

Реализация — модуль `src/factorbot/data/pit.py` с единственной публичной функцией:

```python
def get_fundamentals(as_of: date, permatickers: list[int] | None = None) -> pd.DataFrame:
```

## 5. Вселенная

Пересчитывается на каждую дату ребалансировки, только по данным, доступным на эту дату:

- Обыкновенные акции США, основные биржи (NYSE, NASDAQ, AMEX).
- Исключить: ETF, фонды, трасты, ADR, SPAC.
- Цена на дату ребалансировки > $5.
- Средний дневной оборот за 60 торговых дней > $5 млн.
- Наличие минимум 14 месяцев истории цен (нужно для momentum).
- Финансовый сектор (GICS 40) исключить из value-фактора: Debt/Equity и балансовые метрики там
  несопоставимы с остальными секторами. Для momentum оставить.

Ожидаемый размер вселенной: 1500–2500 бумаг.

## 6. Факторы

### 6.1 Momentum

```
mom_12_1 = adj_close[t - 21] / adj_close[t - 252] - 1
```

Пропуск последнего месяца обязателен: на горизонте до 21 дня работает краткосрочный разворот, который
частично гасит эффект импульса.

Дополнительно рассчитать (для диагностики, не для основного сигнала):
- `mom_6_1` — полугодовая версия
- волатильность дневных доходностей за 126 дней

### 6.2 Value

Использовать **доходности, а не мультипликаторы** — то есть перевёрнутые отношения. Причина: при
отрицательной прибыли P/E уходит в бессмысленный минус и ломает ранжирование, тогда как E/P корректно
помещает убыточную компанию в нижнюю часть шкалы.

```
earnings_yield = net_income_ttm / market_cap
sales_yield    = revenue_ttm / market_cap
book_to_market = equity / market_cap
fcf_yield      = (operating_cf_ttm - capex_ttm) / market_cap
```

`market_cap` считать по цене на дату ребалансировки и числу акций из последнего доступного отчёта.

### 6.3 Нормализация

Одинаковая процедура для всех факторов:

1. Винзоризация по 1-му и 99-му процентилю на каждую дату.
2. Ранг-нормализация внутри сектора GICS → перевод в z-оценку через обратную нормальную функцию.
   Ранг устойчивее z-score к выбросам, которых в фундаментальных данных много.
3. Пропуски не заполнять. Бумага, у которой нет одного из четырёх value-компонентов, получает балл
   по имеющимся; при отсутствии трёх и более — исключается из value-ранжирования.

```
value_score = mean(z_earnings_yield, z_sales_yield, z_book_to_market, z_fcf_yield)
composite   = 0.5 * z_momentum + 0.5 * z_value_score
```

Веса 50/50 задать константой в конфиге, но **не подбирать по результатам бэктеста** (раздел 9).

## 7. Портфель

- Отбор: топ-30 по `composite`.
- Веса: равные (1/30). Взвешивание по баллу не даёт устойчивого преимущества и увеличивает концентрацию.
- Лимит на сектор: не более 30% портфеля. При превышении — вытеснять худшие по баллу бумаги сектора.
- Ребалансировка: последний торговый день месяца, исполнение по цене открытия следующего дня.
- Буферизация для снижения оборота: бумага, уже находящаяся в портфеле, удерживается, пока остаётся
  в топ-45. Это заметно снижает turnover без ухудшения сигнала.

### 7.1 Режимный фильтр

На каждую дату ребалансировки:

```
if SPY.close < SPY.sma_200:
    портфель = 100% SHY (короткие Treasuries)
else:
    портфель = топ-30 по composite
```

Фильтр применяется к портфелю целиком, а не к отдельным бумагам. Реализовать как **отключаемый флаг** —
результаты обязательно сравнить с версией без фильтра.

## 8. Издержки

Не опция, а обязательная часть модели:

- Комиссия: 0 (современные брокеры США), но параметр оставить.
- Проскальзывание + половина спреда: **10 б.п. на сторону** для бумаг с оборотом > $50 млн/день,
  **25 б.п.** для остальных.
- Влияние на цену игнорировать, но зафиксировать в отчёте предполагаемый размер капитала
  ($1–10 млн; выше этого допущение перестаёт работать).

Отчёт должен показывать доходность **до и после издержек**. Разрыв между ними — индикатор того, насколько
стратегия чувствительна к обороту.

## 9. Протокол защиты от переподгонки

Самый важный раздел документа.

### 9.1 Разделение выборки

| Период | Назначение |
|---|---|
| 1999–2012 | In-sample. Разработка, отладка, любые эксперименты |
| 2013–2019 | Валидация. Проверка не чаще одного раза на крупную версию |
| 2020–настоящее | **Hold-out. Открыть один раз, в самом конце** |

Данные hold-out периода не должны загружаться в память во время разработки. Физически разделить файлы.

Глубина Sharadar (цены и фундаментал с 1998 г.) делает это разбиение исполнимым в исходном виде.
In-sample охватывает крах доткомов и 2008 год, валидационный период — годы отставания value,
hold-out — разворот 2020–2022 и последующий рынок. Если бы источником был Alpaca (история с 2016 г.),
протокол пришлось бы заменять на walk-forward с существенно меньшей статистической силой.

### 9.2 Правила

1. **Вести журнал испытаний.** Каждый прогон бэктеста с изменёнными параметрами записывать в
   `experiments.log`: дата, что изменено, результат. Число испытаний нужно для оценки того, насколько
   лучший результат объясним простым перебором.
2. **Требовать плато, а не пик.** Построить карту чувствительности по каждому параметру (окно momentum
   9/12/15 мес., размер портфеля 20/30/40/50, порог SMA 150/200/250). Если результат хорош только при
   одном значении и резко падает у соседних — это подгонка, а не эффект.
3. **Не оптимизировать веса факторов.** 50/50 — априорный выбор. Подбор весов по истории почти
   гарантированно даст переподгонку на двух факторах и коротком ряде.
4. **Тест на перемешанных данных.** Прогнать стратегию на случайно перетасованных сигналах: результат
   должен быть неотличим от нуля. Если и там «работает» — в коде утечка будущего.
5. **Deflated Sharpe Ratio** (Bailey & López de Prado) с поправкой на число испытаний из п.1.

### 9.3 Признаки, что что-то не так

Насторожиться и искать ошибку, если бэктест показывает:

- Sharpe > 1.5 на месячной ребалансировке акций
- Максимальную просадку меньше 25%
- Отсутствие убыточных лет
- Резкий рост качества результатов после добавления мелкой детали

Реалистичный ориентир для честно построенной версии: CAGR на несколько процентных пунктов выше S&P 500,
Sharpe 0.6–0.9, максимальная просадка 35–50%.

## 12. Тесты

Обязательное покрытие:

- `pit.py`: тест, что запрос на дату T не возвращает записей с `available_from > T`. Ключевой тест проекта.
- Momentum на синтетическом ряде с известным ответом.
- Обработка сплита 2:1 — momentum не должен зафиксировать падение на 50%.
- Компания с отрицательной прибылью попадает в нижний дециль earnings_yield, а не в верхний.
- Делистингованная бумага даёт −100%, а не выпадает из расчёта.
- Сумма весов портфеля равна 1 на каждую дату.
- Соблюдение лимита по сектору.

## 13. Этапы

1. **Слой данных + PIT-доступ.** Ничего не строить дальше, пока тест из раздела 12 не проходит.
2. **Momentum отдельно**, без value и без фильтра. Сверить с известными результатами по фактору.
3. **Value отдельно.**
4. **Композит.**
5. **Режимный фильтр**, сравнение с версией без него.
6. **Карты чувствительности** (раздел 9.2).
7. **Валидационный период.**
8. **Hold-out.** Один прогон. Результат принимается как есть, без последующих правок.

Если на шаге 8 стратегия разваливается — это нормальный и полезный исход. Правка кода после просмотра
hold-out превращает его в очередной in-sample и уничтожает единственную честную проверку в проекте.
