# factorbot

Бэктест композитной стратегии **Momentum + Value** на акциях США по ТЗ проекта.

> Исследовательский бэктест, не торговая система. Модуль отправки ордеров в объём
> работ не входит и не создаётся до прохождения всех проверок раздела 9 ТЗ.
> Ничто здесь не является инвестиционной рекомендацией.

Главный критерий — **достоверность, а не доходность**. Все решения ниже
подчинены защите от look-ahead bias и от переподгонки.

## Состояние: этап 6 из 8

| Этап | Что | Статус |
|---|---|---|
| 1 | Слой данных + PIT-доступ | **готов, гейт зелёный** |
| 2 | Momentum отдельно | **код готов, сверка с известными результатами не сделана** |
| 3 | Value отдельно | **код готов, сверка не сделана** |
| 4 | Композит | **готов** |
| 5 | Режимный фильтр | **готов** |
| 6 | Карты чувствительности | **готовы** |
| 7 | Валидационный период | не начат |
| 8 | Hold-out, один прогон | не начат |

ТЗ 13: `factors/` не создаётся, пока ключевой тест раздела 12 не проходит. Он
проходит, поэтому этап 2 открыт.

**Что именно не закрыто на этапах 2–4.** ТЗ 13.2 требует не только посчитать
momentum, но и сверить результат с известными результатами по фактору. Сверять
пока не с чем: реальной выгрузки Sharadar в проекте нет. Всё, что проверено, —
проверено на синтетических рядах с заранее известным ответом. Это ловит ошибки
знака, окна и таймингов, но не отвечает на вопрос, воспроизводит ли реализация
опубликованные цифры по фактору. До этой сверки цифры любого прогона — проверка
проводки, а не результат.

**Исполнение ордеров.** Вне объёма до прохождения проверок раздела 9 (ТЗ 2).
Когда дойдёт очередь, в нём должны появиться: лимит на одного эмитента,
стоп-лоссы, сверка списка с `/v2/assets` перед отправкой заявок. Разрешённые
ТЗ 4.6 операции — торгуемость и сверка цен — работают (см. ниже); функции,
отправляющей заявку, в проекте нет намеренно.

## Ключи

```bash
cp .env.example .env      # и заполнить
```

`.env` в git не попадает — репозиторий на GitHub, а опубликованный ключ находят
сканеры за минуты. В репозитории лежит только `.env.example`. Для CI то же
значение кладётся в secrets репозитория.

Что читается из окружения:

| Переменная | Зачем |
|---|---|
| `NASDAQ_DATA_LINK_API_KEY` | Sharadar — исследовательские данные (ТЗ 4.2) |
| `ALPACA_API_KEY_ID` / `ALPACA_API_SECRET_KEY` | только торгуемость и сверка цен (ТЗ 4.6) |
| `FACTORBOT_UNLOCK_HOLDOUT` | замок hold-out (ТЗ 9.1), держать пустым до конца |

### Сетевой доступ

В облачной сессии Claude Code сеть ограничена политикой окружения, и `data.nasdaq.com`
в список Trusted не входит. Окружение правится через селектор облака на
claude.ai/code (иконка над полем ввода) → шестерёнка → **Network access: Custom**.
Домены, по одному в строке, без схемы и порта:

```
data.nasdaq.com
*.s3.amazonaws.com          # bulk-выгрузка отдаёт ссылку на архив уже на S3
api.alpaca.markets
paper-api.alpaca.markets
data.alpaca.markets
```

Галочку «Also include default list of common package managers» надо оставить:
без неё отвалится установка пакетов. Изменения применяются к новым сессиям —
текущая продолжает работать со старой политикой.

Проверить, что отдаёт ключ, до запуска суточной загрузки:

```bash
python -m factorbot.data.build --check-access
```

Как читать вывод:

| Что напечатано | Что это значит |
|---|---|
| `сеть: ProxyError` | Домен не разрешён сетевой политикой окружения — см. выше |
| `QELx06 ... speed limit` | Ключ временно отключён за частоту запросов. Проходит само; повторять сразу нельзя, счётчик продлевается |
| `QEPx05 ... not subscribed` | Домен открыт, ключ работает, но таблицы нет в тарифе |
| `доступна` | Всё в порядке |

Проверка идёт с паузой между таблицами и прекращается на первом отказе по
частоте: бесплатный ключ Nasdaq отключается целиком, а не поэндпоинтно.

Урезанный тариф — обычное дело. `TICKERS`, `SEP`, `SF1` обязательны: без них
собирать нечего, и сборка честно падает. `ACTIONS` и `DAILY` пропускаются с
предупреждением. Пропуск `ACTIONS` — не мелочь: без неё банкротство выглядит как
исчезновение бумаги из выборки, а не как −100% (ТЗ 4.1), и доходность
value-стратегии завышается систематически. На таком ключе можно отлаживать
конвейер, но нельзя принимать результат.

## Сборка базы

```bash
python -m factorbot.data.build --config config/strategy.yaml
```

Что происходит:

1. Bulk-выгрузка `TICKERS`, `SEP`, `SF1`, `ACTIONS`, `DAILY` (`qopts.export=true`).
   Сырые архивы кэшируются в `data/raw/`; повторный запуск за те же сутки сеть не трогает.
2. Нормализация к схемам ТЗ 4.7. Все соединения — по `permaticker` с интервалом дат
   владения символом, а не по `ticker`.
3. Запись в `data/processed/full.duckdb`.
4. Разрезание на файлы периодов ТЗ 9.1.

## Прогон бэктеста

```bash
python -m factorbot.run --period in_sample --strategy momentum  --note "что изменено"
python -m factorbot.run --period in_sample --strategy value     --note "что изменено"
python -m factorbot.run --period in_sample --strategy composite --note "что изменено"

# ТЗ 7.1: версию с фильтром обязательно сравнить с версией без него
python -m factorbot.run --period in_sample --strategy composite --regime both

# разложение вклада и запись состава вселенной по датам
python -m factorbot.run --period in_sample --strategy composite \
    --decompose --save-universe
```

`--decompose` печатает momentum, value и композит рядом (ТЗ 10) и отдельно
отмечает случай, когда композит хуже лучшей из своих половин: это не обязательно
ошибка, но повод спросить, зачем в нём вторая половина.

`--save-universe` пишет состав вселенной по датам в таблицу `universe` (ТЗ 4.7).
Без неё нельзя ответить, почему бумага не куплена, — балл низкий или её вообще
не было в отборе. Таблица перезаписывается целиком: смешивать в ней прогоны с
разными порогами бессмысленно.

Печатает отчёт ТЗ 10 — CAGR, волатильность, Sharpe, Sortino, максимальную
просадку и её длительность, отставание от SPY в месяцах, оборот, доходность по
годам рядом с бенчмарком — в двух колонках, до и после издержек (ТЗ 8). Разрыв
между колонками показывает, насколько результат держится на обороте.

Каждый прогон дописывается в `experiments.log` (ТЗ 9.2.1). Число испытаний
понадобится для поправки Deflated Sharpe Ratio: без неё лучший результат
неотличим от результата перебора.

В конце отчёта печатаются признаки ТЗ 9.3 — Sharpe выше 1.5, просадка мельче 25%.
Это не проверка корректности, а повод искать ошибку у себя.

Балл считает стратегия целиком, включая нормализацию, а движок отвечает только
за отбор, исполнение и учёт. Иначе не выражается ТЗ 6.3: value нормализует четыре
компонента по отдельности и усредняет их z-оценки, и одним вызовом на выходе это
не получается.

Устройство дня исполнения: сигнал считается по закрытию последнего торгового дня
месяца, сделки проходят по открытию следующего (ТЗ 7). Между сигналом и сделкой
всегда стоит ночь, и ни одна цена, по которой торгуем, не участвовала в расчёте
того, что покупать. Бумага, ушедшая с биржи за эту ночь, не покупается — так же,
как её отсеет сверка с `/v2/assets` на живых деньгах (ТЗ 4.6.1).

## Сверка с контрольным источником (ТЗ 4.4)

```bash
python -m factorbot.data.daily_check --period in_sample
```

DAILY содержит готовые `pe`, `pb`, `ps`, `marketcap`. Для сигналов они не
используются — всё считается самим из цен и AR-измерений. Но как контрольный
источник таблица незаменима: ТЗ 4.4 формулирует прямо, что при систематическом
расхождении надо искать ошибку у себя.

Ключевое слово — **систематически**. Расхождение по отдельной бумаге ожидаемо:
у поставщика другая прибыль, другой капитал, возможно разводнённые акции вместо
базовых. Поэтому проверка смотрит на медиану расхождения по срезу, а не на
худшие случаи. Толстый хвост при неподвижной медиане — это разница определений;
уехавшая медиана — это мы.

Постоянное отношение, кратное тысяче, распознаётся отдельно: капитализация у
поставщика в миллионах, у нас в долларах, и без этой проверки первый же прогон
сообщил бы о расхождении в миллион раз.

## Защита от переподгонки (ТЗ 9.2)

```bash
python -m factorbot.sensitivity --strategy composite --period in_sample
```

Печатает три вещи разом.

**Карты чувствительности (ТЗ 9.2.2)** по сетке из ТЗ: окно momentum 9/12/15
месяцев, портфель 20/30/40/50 бумаг, порог SMA 150/200/250. Для каждой оси —
вердикт «плато» или «пик». Пик означает, что результат держится на одном значении
и рушится у соседних: это подгонка, а не эффект. Буфер меняется вместе с размером
портфеля, полтора состава как в ТЗ 7 — иначе при пятидесяти бумагах буферная зона
оказалась бы меньше самого портфеля.

**Тест на перемешанных данных (ТЗ 9.2.4).** Баллы случайно тасуются между
бумагами, всё остальное остаётся как есть. Читать надо не уровни, а p-значение:
буквально «неотличим от нуля» перемешанный прогон не бывает никогда, потому что
случайный портфель акций зарабатывает рыночную бету. Больше того, у любой
long-only стратегии перемешанный Sharpe близок к настоящему по той же причине.
Признаком утечки является другое — когда случайный отбор обгоняет **бенчмарк** с
большим отрывом. Без бенчмарка тест честно говорит, что ответа не знает.

**Deflated Sharpe (ТЗ 9.2.5).** Число испытаний берётся из `experiments.log`
(вот зачем его ведут), разброс Sharpe между испытаниями — из карт
чувствительности. Обычный Sharpe отвечает на вопрос «отличается ли результат от
нуля», а после двадцати прогонов нужен ответ на другой: «не объясняется ли он
перебором».

Минимальное достижимое p-значение равно 1/(n+1), поэтому перестановок по
умолчанию двадцать: с пятью до 0.05 не добраться в принципе.

## Торговые правила

Сводка того, что бот покупает и продаёт. Всё задано в `config/strategy.yaml`,
констант в коде нет.

### Что покупается (ТЗ 5)

| Правило | Значение |
|---|---|
| Тип бумаг | Обыкновенные акции США |
| Биржи | NYSE, NASDAQ, AMEX |
| Исключено | ETF, ETN, фонды, трасты, ADR, SPAC, варранты, привилегированные |
| Цена на дату ребалансировки | выше $5 |
| Средний оборот за 60 дней | выше $5 млн в день |
| История цен | не меньше 14 месяцев |
| Финансовый сектор | в momentum участвует, из value исключён |

Коротких продаж нет: стратегия только длинная. Продажа происходит либо на
ребалансировке, когда бумага выпала из топ-45, либо по стоп-лоссу, либо при
делистинге.

### Сколько покупается (ТЗ 7)

Топ-30 по композиту, равные веса — 3.33% на бумагу. Не более 30% портфеля в
одном секторе. Бумага, уже находящаяся в портфеле, удерживается, пока остаётся
в топ-45, — это заметно снижает оборот без ухудшения сигнала.

Ребалансировка в последний торговый день месяца, исполнение по цене открытия
следующего дня.

### Лимиты и стопы (вне ТЗ)

Секция `risk` в конфиге. **В ТЗ этого нет** — раздел 7 описывает портфель без
стоп-лоссов. Поэтому всё выключено по умолчанию, а результат обязан сравниваться
с версией без него, как ТЗ 7.1 требует для режимного фильтра:

```bash
python -m factorbot.run --period in_sample --strategy composite --stops both
```

| Параметр | По умолчанию | Зачем |
|---|---|---|
| `stop_loss.enabled` | `false` | Добавка сверх задания, включается осознанно |
| `stop_loss.threshold` | `0.30` | Ловит катастрофу бумаги, а не рыночный шум |
| `stop_loss.quarantine_months` | `1` | Чтобы стоп не превращался в карусель |
| `max_position_weight` | `0.05` | Предохранитель на узкую вселенную |
| `max_trades_per_week` | `null` | Ограничитель стоп-выходов, не ребалансировки |

Три вещи про стоп-лосс, которые надо знать до его включения.

**Он не срабатывает внутри дня.** Внутридневные данные вне объёма работ (ТЗ 2),
и притворяться, что мы знаем минимум дня, нельзя. Условие проверяется по
закрытию, сделка идёт по открытию следующего дня. На реальном стоп-ордере
исполнение было бы хуже — он срабатывает по пути вниз. Значит наша оценка
оптимистична.

**Он не спасает от гэпа.** Бумага, открывшаяся на 40% ниже, продаётся по этой
цене, а не по уровню стопа. Есть тест ровно на это.

**Узкий порог работает против value.** Этот фактор по построению покупает то,
что падало. Стоп в 5–10% на месячной стратегии режет обычную волатильность и
превращается в генератор оборота; при пороге ниже 15% в лог уходит
предупреждение.

Лимит сделок в неделю ограничивает только стоп-выходы. Ребалансировку он не
трогает: она происходит раз в месяц по построению, и откладывать её значило бы
менять стратегию, а не ограничивать риск.

## Alpaca: торгуемость и сверка цен (ТЗ 4.6)

```bash
python -m factorbot.data.alpaca_sync map        # /v2/assets → таблица alpaca_map
python -m factorbot.data.alpaca_sync reconcile  # SEP.closeadj против баров Alpaca
```

`map` строит карту `permaticker` → символ Alpaca с флагами `tradable` и
`fractionable` и датой сверки. Бумаги, которых на площадке нет (OTC, отдельные
классы акций), остаются в карте со значением `tradable=False`: их надо отсеивать
осознанно и видеть в отчёте, а не терять на молчаливом соединении.

Делистингованные бумаги в карту не попадают вовсе. Символ ушедшей компании
переиспользуется, и сопоставление её с сегодняшним владельцем того же тикера
дало бы карту, по которой заявка уходит не в ту бумагу (ТЗ 4.5). Здесь эта
ошибка стоит денег, а не строчки в отчёте.

`reconcile` сравнивает `SEP.closeadj` с барами Alpaca на пересекающемся отрезке
(2016+, глубже история Alpaca не идёт). Сравниваются относительные ряды, а не
уровни: обе стороны корректируют дивиденды от своей базовой даты, поэтому
абсолютные цены расходятся законно. Расхождение больше 0.5% на ликвидных бумагах
— сигнал об ошибке обработки корпоративных действий с чьей-то стороны, и
разбирать его надо до прогонов, а не после.

Обе операции проверены на живом API. Карта строится из настоящего ответа
`/v2/assets` (около 13 400 торгуемых инструментов), делистингованные бумаги в неё
не попадают, отсутствующие остаются с `tradable=False`. Сверка проверена на
реальном сплите AAPL 4:1 от 2020-08-31: совпадающие ряды с разным уровнем цен
расхождений не дают, необработанный сплит находится ровно в день сплита.

Отправки ордеров в проекте нет и не будет до прохождения проверок раздела 9
(ТЗ 2). Это ограничение задачи, а не техническое.

## Разделение выборки (ТЗ 9.1)

```
data/processed/in_sample.duckdb    1999–2012   разработка
data/processed/validation.duckdb   2013–2019   не чаще раза на крупную версию
data/processed/holdout.duckdb      2020–…      открыть один раз, в самом конце
```

Файлы отдельные, hold-out под замком:

```python
from factorbot.data.periods import open_period
conn = open_period("in_sample", "data/processed")     # работает
conn = open_period("holdout",   "data/processed")     # HoldoutLocked
```

Снять замок можно только осознанно: `FACTORBOT_UNLOCK_HOLDOUT=1`.

## Правило, на котором держится проект (ТЗ 4.8)

Единственная точка доступа к фундаменталу — `factorbot.data.pit`. Прямых обращений
к таблице отчётности из остального кода нет ни на чтение, ни на запись.

```bash
bash scripts/check_pit_boundary.sh
```

Проверка стоит в CI. Она груба — обычный grep по имени таблицы — и однажды начнёт
мешать. Мешать она должна: look-ahead попадает в проект не через явную ошибку, а
через одну невинную строку в стороннем модуле.

Инварианты `get_fundamentals`:

* только as-reported измерения `ART`/`ARQ`; `MR*` отвергаются на входе и вообще не
  попадают в базу при загрузке;
* одна строка на `permaticker`: самый поздний **доступный отчётный период**, внутри
  него — самое позднее доступное раскрытие. Сортировка по одному `available_from`
  вернула бы устаревший квартал, если амендмент к нему подан позже следующего отчёта;
* пропуски не заполняются: компания без доступных строк отсутствует в результате,
  а не приходит строкой из NaN;
* пост-условие проверяется на выходе `assert`-ом, независимо от тестов.

записей из будущего; momentum на синтетическом ряду с известным ответом; сплит
2:1 не даёт падения на 50%; компания с отрицательной прибылью оказывается внизу
шкалы `earnings_yield`, а не наверху; делистингованная бумага даёт −100%, а не
выпадает из расчёта; сумма весов равна 1 на каждую дату; лимит по сектору
соблюдается.

Четыре дефекта нашлись тестами, а не чтением кода: позиции не переоценивались
между ребалансировками; бумага, ушедшая с биржи за ночь, покупалась повторно и
делистинг списывался с неё дважды; лимит сектора проверялся в штуках вместо
весов; литеральный процент в шаблоне лога превращал предупреждение о недоступной
ACTIONS в traceback логгера, то есть в ничто.

Синтетическая база в `tests/conftest.py` написана руками под конкретные ловушки:
амендмент, поданный позже следующего отчёта; два периода, раскрытые одним днём;
компания только с балансовым измерением; переставший отчитываться эмитент.
Тесты на реальной выгрузке SF1 недетерминированы — поставщик правит данные, и
зелёный тест краснеет завтра без изменений в коде.

## Отклонения от ТЗ

Каждое сделано осознанно; если какое-то не устраивает — правится в одном месте.

1. **Ключ таблицы отчётности.** ТЗ 4.7: `(permaticker, dimension, reportperiod)`.
   В коде добавлен `available_from`. Иначе амендмент затирает оригинал, и PIT-выборка
   на дату до подачи амендмента вернёт пересмотренную цифру — тот самый look-ahead,
   ради борьбы с которым написан весь модуль.
2. **Сигнатура `get_fundamentals`.** ТЗ 4.8: `(as_of, permatickers=None)`. В коде
   первым аргументом идёт соединение, добавлен обязательный `dimension`.
   Соединение явное, потому что глобального быть не должно: базы периодов физически
   разные, и hold-out нельзя открыть по умолчанию. `dimension` обязателен, потому что
   ТЗ 4.3 разводит потоковые величины (`ART`) и балансовые (`ARQ`).
3. **Знак `capex`.** Поставщик отдаёт отток отрицательным, и это значение сохраняется
   как есть. Формула ТЗ 6.2 `fcf = opcf - capex` записана для положительного capex;
   при принятом знаке считать надо `opcf_ttm + capex_ttm`. На этапе 3 это будет
   единственной строкой в `factors/value.py`, но ошибиться в ней стоит всего фактора.
4. **`is_stale` / `staleness_months`.** В ТЗ нет. Компания, не отчитывающаяся дольше
   9 месяцев, обычно готовится к делистингу, и её последний баланс уже не описывает
   реальность. Это флаг, а не фильтр: решение принимает вселенная (ТЗ 5).
5. **Таблица `daily_control`.** В перечне схем ТЗ 4.7 её нет, но ТЗ 4.4 требует
   держать `DAILY` как контрольный источник. Для сигналов не используется.
6. **Кривая эквити начинается с первой позиции**, а не с первой даты периода.
   В начале выборки вселенная пуста — бумагам нужно 14 месяцев истории (ТЗ 5).
   Плоский участок до первой покупки не является результатом стратегии, но
   попадает в метрики и занижает волатильность, просадку и CAGR.
7. **Лимит сектора проверяется на весах, а не на числе бумаг.** ТЗ 7 задаёт его
   в процентах портфеля. Пока портфель полон, это одно и то же; в узкой вселенной
   позиций меньше, вес каждой выше, и три бумаги из девяти дают сектору 33% при
   лимите 30%. Если лимит недостижим в принципе (три сектора при пороге 30%),
   состав остаётся как есть, а в лог уходит предупреждение.
8. **Безрисковая ставка в Sharpe принята нулевой.** В ТЗ её нет. На горизонте
   1999–2012 это завышает Sharpe примерно на 0.2 — смещение одинаково для всех
   прогонов, но при сравнении с чужими цифрами о нём надо помнить.
9. **Колонка `close_unadj` в таблице цен.** В схеме ТЗ 4.7 её нет. Она нужна в
   двух местах: порог «дороже $5» (ТЗ 5) и капитализация (ТЗ 6.2). Скорректированная
   цена пересчитана от сегодняшней базы, а число акций из отчёта — «тогдашнее»;
   перемножив их, для компании со сплитом получим капитализацию, отличающуюся
   в разы, и весь value-фактор поедет.
10. **Бумага без одного из факторов остаётся в композите.** ТЗ 5 исключает финансы
    из value, но требует оставить их для momentum. Буквальная формула
    `0.5 * z_mom + 0.5 * NaN` даёт NaN и выкидывает такую бумагу из портфеля
    вовсе — то есть исключает и из momentum тоже. Вес недостающего компонента
    перераспределяется на имеющийся, и композит финансовой бумаги равен её
    z_momentum. Подстановка нуля была бы заполнением пропуска, запрещённым ТЗ 6.3,
    и занижала бы балл систематически.
    Цена решения: балл по одному фактору шумнее среднего двух, поэтому такие
    бумаги чаще попадают в оба хвоста, а отбор берёт верхний. Проверять на разборе
    вклада по секторам (ТЗ 10) и на карте чувствительности (ТЗ 9.2.2).
11. **Скользящая средняя считается по скорректированному ряду.** ТЗ 7.1 пишет
    `SPY.close`. На нескорректированной цене сплит создаёт мгновенный разрыв,
    средняя ломается, и фильтр выдаёт ложное пересечение на ровном месте.
    Дивидендный дрейф на окне в 200 дней — величина второго порядка рядом с этим.
12. **Риск-офф до появления SHY проводится в деньгах.** ETF начал торговаться в
    июле 2002, а in-sample по ТЗ 9.1 начинается в 1999 году: первые три года
    уходить физически некуда. Капитал остаётся в деньгах под нулевую ставку.
    Это занижает результат риск-офф периодов 2000–2002, то есть ошибается против
    фильтра, а не в его пользу.
13. **Признак утечки в тесте на перемешанных данных.** ТЗ 9.2.4 пишет, что
    результат на перемешанных сигналах должен быть неотличим от нуля. Буквально
    это не выполняется никогда: случайный портфель акций зарабатывает рыночную
    бету, и у long-only стратегии перемешанный Sharpe близок к настоящему по той
    же причине. Проверка построена иначе — на p-значении (есть ли преимущество
    над случайным отбором) и на сравнении перемешанного результата с бенчмарком
    (не обгоняет ли случайный отбор рынок неправдоподобно). Первая версия
    проверки сравнивала перемешанный результат с настоящим и срабатывала бы
    всегда, то есть была бы бесполезной.
14. **Разогрев при разрезании файлов.** В файл периода кладутся цены за 430 дней до
   его начала. Без этого momentum на первой ребалансировке периода не считается
   (нужно 252 торговых дня, ТЗ 6.1). Утечки нет: данные прошлого относительно начала
   периода. Отчётность кладётся целиком до верхней границы, без нижней, — иначе
   давно не отчитавшаяся компания исчезает из вселенной из-за одного лишь разрезания.

## Журнал испытаний

Каждый прогон с изменёнными параметрами пишется в `experiments.log`: дата, что
изменено, результат. Число испытаний нужно не для отчётности, а для поправки
Deflated Sharpe Ratio (ТЗ 9.2.5): без него «лучший результат» неотличим от
результата перебора.
